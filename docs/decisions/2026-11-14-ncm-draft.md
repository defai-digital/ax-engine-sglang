> **Superseded on 2026-11-14** by [Track A v2](2026-11-14-track-a-v2-concept-spine.md). No GPU run was
> made. The design below is kept as a record.

Supersedes the "start from DFlash2 only" part of
[2026-11-14-retarget-qwen38-27b.md](2026-11-14-retarget-qwen38-27b.md). The target (Qwen3.8-27B), the

## Why this was reopened
The project owner pointed out that the plan no longer used any NCM idea. Re-reading the paper
(arXiv 2610.14162) and the released code showed that our earlier negative result was not a fair
test of NCM:

| NCM paper | Our earlier plan-mode test |
|---|---|
| Tokenizer reconstructs 99.8-99.99% of tokens | 66-84% |
| Input codes corrupted at a mean rate of 0.50, decreasing over levels ("greatly improves quality") | 0.1, flat |
| 8-12 levels (more levels are better) | 3-4 |
| 50k-350k updates | 2,000 |
| - | 0.8B stand-in verifier, separate small encoder, no target hidden states |

Two reviewers (codex gpt-6-astra, Qwen 4 Max; `docs/reviews/2026-11-14-ncm-rethink-*.md`) agree the
old experiment does not reject NCM and that it should be reopened as a bounded track.

## Where NCM could have a real advantage (hypotheses, not results)
1. **Long blocks.** Measured on B200 (SGLang, greedy, no thinking), DFlash2 commits 7.5 tokens per
   round on code with a block of 8: the block cap limits it, not accuracy. A one-pass drafter's
   later positions decay because each position is predicted without knowing the others. A code
   hierarchy fixes shared choices (identifiers, syntax, structure) at coarse levels first, so a
   32-token block may keep a higher survival rate at positions 9-32.
2. **Correction across levels.** Later levels can repair earlier ones (central to the paper's
   Sudoku result).
3. **Adaptive compute.** Early levels are short, and a round can stop after level k.
4. **Sampled decoding.** DFlash2 drops to about 4.2 of 8 with temperature 1.0 and thinking. A
   latent hierarchy models the joint block. The reviewers disagree on how much this helps: with
   exact-match verification even a perfect proposal collides with the target sample only with
   probability sum p^2; shared-noise (Gumbel) verification needs a separate correctness argument.
   This is deferred until the greedy result is known.

What does not transfer: the paper's speed-ups (measured against diffusion models only), semantic
similarity of drafts (verification is exact-token), and tokenizer compression by itself.

## The structural risk
Exact-prefix acceptance rewards the easy early tokens. A global coarse code summarises the whole
block, including far tokens that cannot be predicted, and an error in it can spoil the early
tokens. The design counters this with heavy code corruption, code dropout at the token level and a
direct path from the target's hidden states to the token level. Whether that is enough is exactly
what the controls measure.

## NCM-Draft v1
- **Block:** 32 tokens drafted after the last committed token (the anchor).
- **Conditioning:** hidden states of the frozen Qwen3.8-27B tapped at layers 5/19/33/47/61 (the
  DFlash2 / DSpark taps), scale-normalised, concatenated and projected to the decoder width. They
  are free at serving time (the verify pass computes them) but exist only for positions before the
  anchor; the anchor enters as a token embedding. Training and evaluation use this convention.
- **Hierarchy:** block residual VQ codes at levels [1, 2, 4, 8, 16, 32] (variant: [1, 2, 4, 8, 16]),
  then one token level whose logits go through the frozen target LM head, so fidelity is not
  capped by the tokenizer.
- **Paper recipe copied:** corruption mean 0.50 decreasing over levels with clean labels, nested
  dropout in the tokenizer, block-diagonal attention per level, equal level weights (alpha = 1).
- **Decoder:** 6 layers, d = 1024 (about 140M trainable with the tap projection); 7 passes per block.
- **Data:** the 27B's own greedy, non-thinking answers (code, math, chat), 40k prompts per domain to
  start; the speed benchmark's prompts are added as held-out domains.

## Controls (same conditioning, data, decoder size and steps)
| Config | What it removes |
|---|---|
| `direct_b32` | the hierarchy: 32 tokens in one parallel pass (the one-pass block drafter) |
| `chunks_b32` | the codes: coarse-to-fine in token space, chunks [1,1,2,4,8,16], 6 passes |
| `ncm_b32_k5` | the full-resolution code level |

NCM earns its place only if removing the hierarchy removes the gain.

## Metrics and gates
- Free-running only: the model drafts from its own predictions. Reported per domain as tokens per
  verify round and as the survival curve P(accepted prefix >= j) for j up to 32.
- **Gate 1 (tokenizer):** `tok_b32_k6` reconstructs >= 99% of held-out tokens (aim 99.8%). Below
  97% the code path is not worth training on.
- **Gate 2 (hierarchy):** `ncm_b32_k6` commits >= 10% more tokens per round than both controls on
  code and math, and its survival at j = 16 is higher than `direct_b32`'s.
- **Gate 3 (against DFlash2):** on the benchmark prompts, more tokens per round than DFlash2's
  measured value at a projected draft cost that still wins end to end. Only then is the SGLang
  integration (the project gate: >= 1.5x tuned MTP and >= 1.1x the best public drafter) started.
- If gate 2 fails after training has plateaued, the result is reported as negative and the
  DFlash2 fine-tuning line continues with the best control.

## Reviewer estimates (subjective)
>= 10% over DFlash2: greedy code/math 25-40%, sampled thinking 30-50%, chat 20-45%.
>= 1.5x tuned MTP: 30-60%. >= 3x tuned MTP: 1-15%.
