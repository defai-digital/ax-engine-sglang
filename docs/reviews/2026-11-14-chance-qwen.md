# Winning chance and design review: qwen

Independent review. I read both decision docs, `phase2/drafter.py`, the `track_a/` configs, both ablation reports, and the prior codex/qwen4 reviews. Blunt version: **the latency math kills NCM‑Draft v1 as the lead line, and the sampled‑decoding thesis rests on an incorrect acceptance argument.** Fine‑tuned DFlash2 is the higher‑EV path.

**1. Probabilities (mine, lower than yours).** Arithmetic: DFlash2 = 489 tok/s ÷ 7.5 accept = **15.3 ms/round**; AR 9.8 ms; MTP3 12.4 ms. NCM v1 = 7 sequential drafter passes (~4–8 ms at c=1; small models are launch/latency‑bound, not bandwidth‑bound) + verify‑32 (~13–17 ms) ≈ **18–25 ms/round**. To beat DFlash2 by 10% (538 tok/s) you need accept ≈ **11–13.5/round vs its 7.5** — a 45–80% acceptance gain just to pay the latency handicap.
- Offline accept > DFlash2, greedy code, *any* variant: **~35–40%** (direct block‑32 can, since DFlash2 is block‑cap‑limited); NCM‑only **~15%**.
- NCM ≥10% over both controls: **~10%**.
- End‑to‑end ≥10%, greedy code/math: **~12%**.
- Sampled+thinking: **~8%**. Chat: **~5%**.
- 3× MTP: **~1–2% code, ~0% chat**. (1.5× MTP, the real gate, is easier: ~30–40%, since MTP accept is only 3.1.)

**2. Design correctness — biggest mistakes.**
(a) **VQ hierarchy is the wrong tool for a lossless drafter.** Only the exact‑match prefix counts; a position‑1 error kills the block regardless of coarse‑plan quality. Quantization adds an irreducible fidelity floor (your tokenizer hit 66–84%; even at the 99% gate, code errors compound across 6 levels). Coarse‑to‑fine helps only if it raises *early‑position* accuracy, but a single global level‑1 code spends the least capacity on the earliest, most valuable tokens. The CPU toy (chunks teacher‑forced 0.95 → free‑running 0.31) already falsifies the token‑space version.
(b) **Fixed block‑32 is wrong for chat/thinking** (accept ~3.2 for everyone): you pay verify‑32 compute for ~3 accepted tokens, worst at c=32. Adaptive length is required and isn't wired into the NCM path (`rollout_codes` always runs all levels).
(c) **7 passes is the core error.** DFlash2's whole advantage is one pass. Each extra pass re‑reads weights + adds launch overhead; codex's own estimate puts drafting at 0.4–0.9 target‑steps. You're buying acceptance at a price needing ~45–80% gain to break even.
(d) d=1024×6 is fine for latency, but the 5120→1024 cross‑attn bottleneck + small capacity cap acceptance for 32‑token exact prediction. Prefer d=2048–3072.
(e) **Greedy non‑thinking training vs sampled+thinking deployment** is a real distribution mismatch; thinking traces branch more. Train on the target's own sampled+thinking outputs.
(f) Chat is entropy‑limited; no architecture fixes accept ~3.2. Win via cheaper rounds/adaptive length, not block‑32.
Also: confirm the **anchor convention** isn't discarding the verified last‑token hidden state (computed free during verify). If DFlash2 conditions on it and you use only an embedding, that's a self‑imposed token‑1 handicap.

**3. What I'd build (2×B200, ~200 GPU‑h).** Lead with **fine‑tuned DFlash2, not NCM.** One‑pass block drafter, same 5 taps, d=3072–5120, 3–5 layers, block 8–16 adaptive; init from DFlash2 (SpecForge); online frozen 27B; train on its own sampled+thinking outputs, 30–100M tokens, prefix‑weighted loss. Add a confidence/length head (stop when marginal accept < cost) and a 2‑candidate tree at positions 1–2. Keep NCM only as a *gated refinement on positions 9–32*, and only if the oracle test shows headroom.
**First falsifying experiment (≤6 GPU‑h, inference‑only):** (i) extend DFlash2 to block 16/32 and measure the survival curve on greedy code; (ii) oracle‑ceiling — feed a one‑pass drafter the *gold* coarse codes and measure acceptance. If extended one‑pass already captures the long‑block gain, or oracle ≈ direct, the hierarchy adds nothing → kill NCM, fine‑tune DFlash2. This tests the thesis before spending on tokenizer+drafter.

**4. Where NCM genuinely adds value.** Adaptive compute (coarse plan predicts block predictability → early stop) and tree branching (top‑k coarse codes → candidate tree). Both are real and absent from DFlash2/DSpark — but both can be done *without VQ*. Re‑drafting the tail from cached verify states is just a refinement pass, not uniquely NCM. "Correcting a rejected block" is useless for lossless (the verifier already emits the right token). Carrying a plan across blocks: marginal. The VQ token‑emission path is not where the value is.

**5. SOTA.** No live web access this session, so I can't verify 2026 releases (DFlash2/DSpark/SpecPilot/JetSpec); your repo already cites the DFlash2 card + a NeMo impl. What you're missing, with sources I can stand behind: EAGLE‑3 feature fusion + training‑time test (arxiv.org/abs/2503.01840); tree verification — SpecInfer (2305.09781), EAGLE‑2 (2406.16858), Sequoia (2402.12374), Medusa (2401.10774); adaptive length — SpecDec++ (2405.19715); lossless sampling couplings — big‑little decoder (2302.07863) and the Gumbel/OT coupling codex cited (openreview GJbrk55Bt8).
**Critical:** the qwen4 review's Gumbel argument is wrong as stated. Output is trivially lossless (always fall back to the target sample), but acceptance ≠ 1−TV(p,q_z) under shared Gumbel noise, and TV‑convexity gives E[1−TV] ≤ 1−TV(E) — the *reverse* of the claimed "≥". So "latent joint modeling raises sampled acceptance" is unproven (codex flags exactly this). Don't make it load‑bearing. Also unaddressed: **DeltaNet recurrent+conv state checkpoint/restore at the accepted boundary** — a real SGLang integration risk.
