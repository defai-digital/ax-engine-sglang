The gold-code ceiling is the constraint I want to check against the NCM setup before ranking the architectures.1. The diagnosis is right, and it is worse than a sampling bug. Gold codes are a function of the target block, so teacher-forced token accuracy is an oracle-assisted decode. NCM reports the same train/inference gap. If you keep codes, rollout should ramp to the greedy policy you ship. Corrective targets are the wrong primary fix: nearest residual code minimizes latent distance, not prefix error, and a bad level-0 code can leave a residual the finer books cannot represent. Targets also move with the current policy. One on/off ablation, off the critical path.

Greedy traces are deterministic, so multimodal continuations are not the failure. What remains is within-level independent argmax, a reconstruction codebook that spends bits on late-block detail, code loss dominating while level-0 usage is about 4%, and a decoder that learns to ignore a plan. Flat 50% rollout from step 0 also trains the token head on garbage plans.

2. A discrete plan of the whole block is a poor fit for exact greedy acceptance. A near-lossless code has the same conditional entropy as the tokens. This VQ spends capacity on token reconstruction, not on what the prefix already determines about positions 0–3. With gold codes, accuracy 0.67 is roughly flat, so accepted length is about 2.0, the geometric sum. The oracle plan does not make the first tokens easy. NCM’s perplexity and ROUGE results are about cheaper approximate generation, not lossless agreement with another model’s greedy path.

Drop the plan unless, at equal GPU-time, free-running accepted length beats direct and chunk by enough to raise projected throughput at least 20%. If oracle-code length is still about 2 after prefix weighting, drop it: there is no headroom above MTP once the 0.8B encode is paid for.

3. In order: (a) Prefix-weighted token loss, steeper than 0.8^j. Use weights proportional to 0.5^j on positions 0–7, plus a small floor. Log P(A≥k) for k=1,2,4,8. (b) Left-to-right chunks with first-chunk size 1. (c) A cached autoregressive baseline from the frozen 0.8B, 4–8 tokens, its own KV cache, no new decoder. If that matches the trained decoder, the decoder is not the bottleneck. Top-k verifier KL on the first 4–8 positions comes after (a). Skip continuous plans and mask-predict until something clears MTP.

4. Stop lossless tokenizer training. Rejection sampling is already the losslessness mechanism. Freeze the codebook used in the running ablation. Resume only if an oracle-plan run with prefix-weighted loss clearly beats the token-only models.

5. Cap the next 24 hours at about 48 GPU-hours. Let the 2k run finish; do not extend it. Start one chunk run: [1,1,2,4,8], gold earlier chunks, prefix weights, same data and steps. Report A = leading exact matches, R = 1+A, and P(A≥k) on prompt-disjoint code and chat. If first-token acceptance is about 1%, the published 1.07 is R and A is about 0.07; do not compare it with the teacher-forced prefix of 2.0. Kill codes unless free-run throughput beats chunk by at least 20%. Continue the winner only if A≥1.5 or position-0 accuracy is past 0.5 and still climbing. Otherwise run the vanilla 0.8B AR baseline, time incremental encode plus draft against one verify, and stop if it cannot project ≥1.3× MTP. No tokenizer steps, no corrective sweep, no H200.

6. I agree with rollout-if-codes-survive, optional corrective targets, prefix weighting, pausing the lossless tokenizer, and the 1.5× MTP gate. I disagree with training later chunks on the model’s own earlier tokens: acceptance only scores histories that matched the verifier. I also disagree that a reconstruction plan is no harder than the first few tokens. The 20% margin versus direct is only a tie-break; both can lose to MTP.

The chunk argument holds across chunks: the first rejected token is scored under gold history. It fails inside a parallel chunk, where tokens never see each other. [2,2,4,8,16] spends the first pass on a pair and the last on 16 tokens you almost never reach. Use [1,1,2,4,8], and stop inference once confidence says the next chunk will not survive.

7. Put the budget on that chunk configuration. It matches the acceptance process, needs no VQ, and keeps the 0.8B as a cached encoder. Leave direct as the control already running. Codes have an oracle ceiling near two accepted tokens and a free-run collapse; they get more hours only if the 2k numbers contradict that ceiling.
